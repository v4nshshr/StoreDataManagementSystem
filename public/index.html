Pipeline 1: Sales & Profit by Category

Calculates total sales and net profit grouped by product categories using $unwind, $lookup, and $group.

MongoDB Aggregation Query (Pipeline 1)
db.orders.aggregate([
  // 1. Unwind embedded order items array into individual documents
  { $unwind: "$items" },

  // 2. Lookup (Join) with products collection to fetch Category
  {
    $lookup: {
      from: "products",
      localField: "items.productId",
      foreignField: "productId",
      as: "product"
    }
  },
  { $unwind: "$product" },

  // 3. Group by Category and sum total sales & profit
  {
    $group: {
      _id: "$product.category",
      totalSales: { $sum: "$items.sales" },
      totalProfit: { $sum: "$items.profit" },
      itemCount: { $sum: 1 }
    }
  },

  // 4. Sort descending by highest sales
  { $sort: { totalSales: -1 } }
]);

Pipeline 2: Monthly Sales & Profit Trend

Extracts year and month from ISO date fields using MongoDB date expressions $year and $month.

MongoDB Aggregation Query (Pipeline 2)
db.orders.aggregate([
  // 1. Group by Year and Month extracted from orderDate field
  {
    $group: {
      _id: {
        year: { $year: "$orderDate" },
        month: { $month: "$orderDate" }
      },
      totalSales: { $sum: "$totals.sales" },
      totalProfit: { $sum: "$totals.profit" },
      orderCount: { $sum: 1 }
    }
  },

  // 2. Project clean period string (YYYY-MM) and round numbers
  {
    $project: {
      _id: 0,
      period: {
        $concat: [
          { $toString: "$_id.year" },
          "-",
          { $cond: [{ $lt: ["$_id.month", 10] }, { $concat: ["0", { $toString: "$_id.month" }] }, { $toString: "$_id.month" }] }
        ]
      },
      totalSales: { $round: ["$totalSales", 2] },
      totalProfit: { $round: ["$totalProfit", 2] },
      orderCount: 1
    }
  },

  // 3. Chronological sorting
  { $sort: { period: 1 } }
]);

Pipeline 4: Shipping Mode Transit

Average delivery days computed via date subtraction arithmetic in $project.

MongoDB Aggregation Query (Pipeline 4)
db.orders.aggregate([
  // 1. Subtract orderDate from shipDate (milliseconds to days)
  {
    $project: {
      shipMode: 1,
      shippingDays: {
        $divide: [{ $subtract: ["$shipDate", "$orderDate"] }, 86400000]
      }
    }
  },
  // 2. Calculate average days per ship mode
  {
    $group: {
      _id: "$shipMode",
      avgShippingDays: { $avg: "$shippingDays" },
      orderCount: { $sum: 1 }
    }
  },
  { $sort: { avgShippingDays: 1 } }
]);

Core Viva Decision: Embedding vs. Referencing

What We EMBEDDED: Order Items in Orders

Decision: Each order document contains an embedded array of items: [...].

  • Atomicity: An order and its line items represent a single transaction created together.
  • Historical Snapshot: Prices and discounts at purchase time remain immutable even if the catalog changes later.
  • Bounded Cardinality: A retail order has only 1–15 items; it will never exceed MongoDB's 16 MB document limit.
What We REFERENCED: Customers in Orders

Decision: Orders only store a reference: customerId: "CG-12520".

  • Unbounded Growth: A loyal customer places hundreds of orders. Embedding orders inside customer documents would exceed the 16MB document limit.
  • Centralized Updates: If Claire Gute changes her address, updating one document in customers avoids modifying 100 historical orders.

NoSQL Viva Examiner Questions & Answers

Read these clear, direct answers to ace your practical exam and viva evaluation!

Q1: What is NoSQL and why did you use MongoDB instead of SQL / MySQL?
Answer: In SQL, data is strictly organized into rectangular tables with rigid schemas and foreign keys. In MongoDB, data is stored as self-contained BSON (Binary JSON) documents. We used MongoDB because retail transactions naturally contain nested items (one order has multiple products). Document models allow embedding related data together for faster reads, avoiding expensive table joins, and providing flexible, agile schema evolution.
Q2: Explain Embedding vs. Referencing in your schema.
Answer:
  • Embedding (1-to-Few): We embedded line items inside orders because an order and its items are created together and represent an immutable transaction snapshot.
  • Referencing (1-to-Many): We referenced customers in orders because a customer can have hundreds of orders over time. Embedding all orders in customer documents would cause unbounded array growth and hit MongoDB's 16MB document size limit.
Q3: What is an Aggregation Pipeline and what are the main stages you used?
Answer: An Aggregation Pipeline processes documents sequentially through stages like an assembly line. The stages used in our project:
  • $match: Filters documents by criteria (like SQL WHERE).
  • $unwind: Deconstructs an array field so each element becomes a separate document.
  • $group: Groups documents by key and computes aggregates using $sum, $avg (like SQL GROUP BY).
  • $project: Reshapes output fields or computes derived values (like SQL SELECT).
  • $sort: Sorts output ascending or descending (like SQL ORDER BY).
  • $lookup: Performs a left outer join with another collection (like SQL LEFT JOIN).
Q4: What indexes did you create and how do they speed up queries?
Answer: Without indexes, MongoDB must perform a COLLSCAN (scanning every document in the collection). With a B-Tree index, it does an IXSCAN in $O(\log N)$ time.
  • Multikey Index on items.productId in orders: Because items is an array, this index creates an entry for every product in every order for fast lookups.
  • Compound Index on { category: 1, subCategory: 1 } in products: Speeds up catalog filtering following the prefix rule.
Q5: What is BSON?
Answer: BSON stands for Binary JSON. It is the binary serialization format MongoDB uses to store documents on disk and over the network. BSON extends standard JSON by adding native data types not found in JSON, such as Date, ObjectId, Int32, Int64, and binary data.
Q6: What is the _id field in MongoDB?
Answer: Every MongoDB document must have a unique primary key called _id. If omitted on insertion, MongoDB automatically generates a 12-byte ObjectId consisting of a 4-byte timestamp, a 5-byte random value, and a 3-byte incrementing counter.
